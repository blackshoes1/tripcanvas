# With J iOS 지도 중심 일정 작성 — 구현 및 검증 기록

작성일: 2026-09-16

이 문서는 [개발 프롬프트](ios-map-first-planning-ux-work-prompt.md)의 A~F와 현재 작업 코드를 대조한 기록이다. **코드 구현, 합성 데이터 검증, 실제 제공처 연결, 운영 반영은 서로 다른 상태로 기록한다.** 모든 완료 기준을 충족했거나 새 TestFlight 빌드가 배포됐다는 보고가 아니다.

작업 기준은 `feat/ios-map-planning`의 `/tmp/tripcanvas-map-planning`이다. 검토 기준이 된 TestFlight 0.1.0 (34)의 `df11e2f` 및 선행 일정 갱신 수정은 보존한다. 선행 PR #224는 아직 미병합 상태다. #225 인증·여행 중 → #226 공통 엔진·API → 현재 iOS UI 브랜치 순서로 검토 단위를 나눴다.

## A. 지도에서 발견하고 날짜 없이 담기

구현한 흐름:

- 일정의 지도 보기에서 `장소 찾기 / 이 날 / 전체`를 고른다. 장소가 없는 여행도 지도 탐색으로 이어지고, 기준 위치가 없으면 지역 선택을 안내한다.
- 지역 선택에서 국내/해외를 명시하고, 선택한 장소로 지도를 이동한다. 지도 탐색 검색은 현재 지도 중심과 화면 범위를 사용하므로 한국어 검색어 자체로 국내를 결정하지 않는다.
- 음식점·카페·관광·숙소 필터, 명시적인 `이 지역에서 찾기`, 검색 결과 목록과 핀을 연결했다. 지도 이동만으로 검색을 연속 실행하지 않는다. 오래된 검색 응답은 버린다.
- 핀 선택은 장소 카드로 이어진다. 확인되지 않은 좌표 탭에는 이름 입력을 요구하고 가장 가까운 상호를 실제 탭한 장소로 추측하지 않는다. 검색 실패·무결과에서는 검색어로 직접 담을 수 있으며 좌표는 미정으로 저장한다.
- 지도 아래 검색/담은 장소 목록을 버튼으로 접고 펼친다. 검색 결과는 검색 핀, 날짜 미정 후보는 별 모양, 일정 장소는 순서 번호로 구분한다. 후보에 방문 순서나 경로를 만들지 않는다.
- 담기 중에는 기존 지도 카메라와 검색 맥락을 유지하도록 지도 컨테이너를 연결했다. 확정 제공자 ID와 요청 키로 중복 쓰기를 방지한다. 응답이 끊겼을 때는 서버 목록을 확인하고 같은 요청 키·본문으로 재시도한다. 제외했던 후보는 별도의 되돌리기 동작을 거친다.
- `provider/providerId`를 후보에서 일정까지 보존한다. Google ID와 Kakao ID를 같은 필드로 섞지 않는다. 이름만 같은 장소나 ID 없는 별도 요청은 임의로 합치지 않는다.

근거: `Features/Map/MapDiscoveryView.swift`, `MapDiscoveryModel.swift`, `PlaceSearchService.swift`, `MapEngineView.swift`, `KakaoMapContainer.swift`, `GoogleMapContainer.swift`, 후보 저장 API·Repository. 검색 범위·요청 키·마이그레이션의 정확한 계약은 [지도 탐색 API 문서](ios-map-planning-api.md)를 따른다.

제한과 남은 확인:

- 화면 탐색 범위는 앱에서 지도 중심부터 가장 먼 모서리까지 20km로 제한한다. 너무 넓으면 확대를 안내한다. 결과 개수와 범위 제한이 있으므로 화면 안 모든 장소를 완전히 수집한다는 의미가 아니다.
- 검색 결과·후보 추가 때 카메라를 보존하는 연결은 구현했지만, 실제 국내/해외 검색부터 5곳 연속 담기·앱 재진입까지의 제공처/운영 서버 통합 흐름은 아직 검증하지 않았다.
- 지도 모드 자체를 떠났다가 다시 생성하는 화면의 검색어·카메라·목록 펼침 상태를 영구 보존하는 기능은 아니다. 드래그로 하단 목록 높이를 조절하는 시트 대신 펼침/접힘 버튼을 사용한다.
- 실제 장소 사진·평점 표시, 오프라인 지도 타일 캐시는 추가하지 않았다.

## B. 날짜 배치와 동선 조정

구현한 흐름:

- `여행 전체 개요`에서 날짜/요일, 제목, 주요 장소, 이동시간·거리, 종료 예상, 체류시간 미정·위치 미정·시간 충돌을 함께 본다. 계산 전과 계산 실패를 구분하고 다시 읽기를 제공한다. 장소 수만으로 과밀을 판정하지 않는다.
- 후보를 배치할 때 목적 날짜와 삽입 위치를 고른다. 일정의 각 장소 뒤에 추가하는 메뉴와 한 곳/여러 곳을 다른 날짜·위치로 옮기는 메뉴가 있다.
- `이 날` 지도는 목록 선택과 핀 선택을 연결한다. 탐색 지도에서 일정 핀을 누르면 해당 날짜의 일정 지도로 이동한다. 날짜를 바꿀 때 이전 날짜의 선택 인덱스를 유지하지 않는다.
- 이동 미리보기는 서버의 기존 하루 계산으로 변경 전후 이동시간·종료 예상·예약 지연을 표시한다. 미조회 경로는 추정으로 남기며 초안을 저장하거나 미리보기만으로 외부 경로 조회를 시작하지 않는다.
- 기존 후보 날짜 추천·그룹 제안을 사용한다. 개인 재배치는 이미 연결된 `candidateId`의 장소 원문을 옮기며 예약·메모·알 수 없는 필드를 새 장소로 재생성하지 않는다.
- 그룹 제안의 문서 저장 응답이 유실되거나 후보 표시만 실패해도 기존 장소를 다시 삽입하지 않는다. 이미 문서에 있으면 실제 날짜의 후보 표시만 복구한다. 연결을 확인할 수 없는 레거시 후보는 이동 성공으로 표시하지 않는다.
- 지도에서 배치한 뒤에는 후보 표시만 실패한 경우도 부모 일정을 다시 읽는다. 문서 저장의 부분 성공이 지도에서 누락되지 않도록 연결했다.
- 문서 이동·삭제 시 기존 후보 참조 갱신을 NAS의 revision CAS 트랜잭션에 연결했다. 삭제 되돌리기는 문서 복구 후 삭제됐던 후보만 다시 `SCHEDULE`하며, 후보 표시 복구만 실패하면 일정 복구 성공과 분리해 안내한다.

근거: `Features/Plan/TripOverviewView.swift`, `PlanMoveSheet.swift`, `PlanPreviewSection.swift`, `TripPlanView.swift`, `TripPlanViewModel.swift`, `Features/Collab/CandidatePlacementSheet.swift`, `CandidateBoardViewModel.swift`, `TripDocument.swift`, `collab.js`, NAS `pgTripRepository.ts`.

제한과 남은 확인:

- 변경 비교는 후보 배치와 날짜·위치 이동 시트에 연결했다. 일반 목록 드래그 재정렬마다 별도 확인 미리보기를 띄우는 방식은 아니다. 기존 드래그는 즉시 저장과 마지막 변경 되돌리기를 사용한다.
- 핀과 목록 선택은 연결했지만 선택 구간만 별도의 선 스타일로 강조하는 기능은 추가하지 않았다.
- ID 없는 레거시 후보, 다른 여행의 후보 ID, 여러 날짜에 복제된 모호한 ID는 추측해서 보정하지 않는다.
- 다른 기기와 동시에 편집하는 실제 NAS 흐름, 미리보기 후 revision 충돌, 후보 표시 부분 실패 후 지도·보드·일정 재진입은 최종 통합 확인이 필요하다.

## C. 하루의 기본 설정과 시간 표현

구현한 흐름:

- 생성 후 여행 이름·시작일·기간과 선택한 날의 제목·출발 시각·전날 종료 장소 이월 여부·기본 이동수단을 수정한다.
- 시작일이 바뀌어도 기존 장소의 달력 날짜와 외부 예약 날짜를 보존한다. 앞에 빈 날을 추가하거나 비어 있는 날만 줄이는 방식이다. 장소뿐 아니라 제목·메모·예산·출발 설정 등이 있는 날도 조용히 삭제하지 않는다.
- 날짜 변경 전후의 일자와 장소 수, 외부 예약 날짜 유지 안내를 보여주고 확인을 받는다. 기간 안에 기존 일정을 보존할 수 없으면 저장을 막고 먼저 정리하도록 안내한다.
- 일정 상단에서 출발·이동·종료를 읽고 체류시간 미정 개수를 확인한다. 미정은 계산상 0분을 유지하되 사용자가 정한 `0분 (바로 이동)`과 구별한다.
- 시각 선택은 분 전체를 제공해 12:07 같은 예약 시각을 입력할 수 있다. 자동 예상 도착, 사용자가 정한 도착, 예약·입장 시각을 구별한다. 비용·숙소 등의 추가 필드는 펼쳐서 편집한다.

근거: `Features/Plan/PlanSettingsView.swift`, `SpotEditorView.swift`, `TripPlanView.swift`, `TripOverviewView.swift`, 공통 `lib.js`/하루 일정 계약.

제한과 남은 확인:

- 출발 장소 전용 새 모델은 만들지 않았다. 다른 출발 장소는 그날 첫 장소로 배치하고 전날 이월을 끄는 기존 앵커 규칙을 사용한다.
- 날짜 축소는 입력이 있는 날을 자동 이동·삭제하는 기능이 아니다. 사용자가 먼저 옮기거나 정리해야 한다. 날짜 변경 미리보기는 일자·장소 수와 예약 안내 중심이며 후보별 영향 전체를 별도 목록으로 설명하지 않는다.
- 식사·휴식을 자동 추가하거나 미정 체류시간을 추천값으로 채우지 않는다.
- 11시 출발, 12:07 예약, 자정 이후 종료, 연박 이월·공항 출발을 실제 앱 조작으로 모두 확인한 상태는 아니다.

## D. 하루 예산과 비용 내역

구현한 흐름:

- 하루 예산과 입력/확인된 비용 합계를 분리하고 예산 미설정·예산 0을 구별한다. 예산 차이는 현재 반영된 비용 기준으로 표시한다. 미정·일부 금액과 미포함 교통비를 안내하고 예산 초과로 장소 추가를 막지 않는다.
- 장소 비용과 식사·입장료·교통·숙박 등 추가 비용, 예약의 하루 배분액·자동 교통비 내역을 확인하고 수정한다.
- 빈 금액은 미정, 명시적인 0은 무료/0원, 일부 금액은 부분 확인으로 보존한다. 1인 금액/일행 전체/기준 미정과 적용 인원을 구분하며 1인 기준만 인원을 곱한다.
- 원화·엔은 정수, 달러·유로·위안은 소수 둘째 자리까지 입력·보존한다. 예약 가격·취소 수수료도 소수를 보존하도록 관련 필드를 바꿨다.
- 원래 통화·금액과 원화 환산을 나눠 표시한다. 폴백 환율은 참고 기준이며 실시간 시세·시세 기준일이 확보된 것처럼 표시하지 않는다.
- 비용 합산은 공통 `dayCostSummary`를 사용한다. 연결된 장소에 금액이 있는 예약의 중복 합산, 예약 날짜별 소수 배분, 수동 교통비와 자동 추정의 중복을 처리한다. 날짜 없는 유료 예약은 합계에서 빠졌다고 표시한다.
- 새 비용 필드의 검증·정규화·API 계약·정적 웹/Next 보존 경로를 함께 변경했다. iOS 저장 성공 후 계산 재조회는 저장 완료와 분리한다.

근거: `Features/Plan/DayCostView.swift`, `Core/Models/DayCost.swift`, `TripBooking.swift`, `lib.js`, Next `dayView.ts`, `dayPlanView.ts`, 비용·Swift 계약 테스트.

제한과 남은 확인:

- 실제 환율 제공처를 새로 연결하거나 여행 전체 예산 편집 화면을 추가한 것은 아니다. 하루별 예산·내역이 이번 UI의 범위다.
- 확인하지 못한 교통비·날짜 없는 예약·일부 비용은 합계에 누락될 수 있다. 현재 합계를 여행 최종 결제액으로 보장하지 않는다.
- 새 비용 데이터를 구형 서버에 다시 저장하면 예전 정규화가 소수를 반올림할 수 있다. API 선배포와 구버전 왕복 확인이 필요하다.
- 합성 비용·계약 테스트와 실제 iOS→NAS→웹 재조회/재저장 검증은 구분한다. 후자는 아직 미검증이다.

## E. 명소 예약 요건과 입장료

구현한 흐름:

- 명소 요건(`필수/권장/예약 없이 입장 가능/확인 필요`)과 개인 예약 완료 상태를 별도 필드로 기록한다. 예약 시각·숙박 연결 ID·페이지 열기에서 완료를 추론하지 않는다.
- 사용자가 확인한 예약 인원, https 예약 페이지, 권종·날짜 등의 메모, 명시적으로 확인한 시각을 입력한다. 링크는 안전한 URL인지 검사하지만 실제 공식 운영자인지 자동 인증하는 것은 아니다.
- 일정 상단의 `예약할 곳`은 명시적 예약 필수이면서 미완료인 장소만 센다. 확인 필요 항목은 필수 건수에 섞지 않는다.
- 장소 카드/편집기에서 한 장소의 참고 정보 연결 상태를 조회한다. 현재 서버는 `NOT_CONNECTED`, `UNKNOWN`, `quote: null`을 반환하고 화면은 직접 확인·입력 경로를 안내한다. 가격·출처·확인 시각을 만들어 넣지 않는다.

**외부 명소 예약 규정·입장료 자동 조회는 미연결이다.** 실제 날짜·권종·성인/어린이 가격, 재고·예약 가능 시간 조회, 참고 가격을 선택해 비용에 반영하는 UI는 완료되지 않았다. 비용에는 사용자가 별도 편집에서 확인한 금액을 직접 적는다. 자동 조회 성공을 보여주는 대역 제공처를 운영 기능에 넣지 않았다.

Google `reservable`이나 일반 가격 범위, 카카오 기본 장소 검색, 기존 호텔/렌터카 시세를 명소 예약 필수 여부·입장권 결제 가격으로 바꾸어 해석하지 않는다. 실제 예약 신청·티켓 구매·결제 자동화도 범위 밖이다.

현재 확보한 데이터와 필요한 계정·상품 매칭·출처/이용 조건은 [명소 예약 데이터 문서](ios-admission-data.md)에 정리했다. 새 파트너 계정·유료 계약은 체결하지 않았다.

## F. 저장 신뢰, 후속 화면, 접근성

구현한 내용:

- **저장/계산:** 문서 저장 완료를 계산 응답 대기에 묶지 않는다. 저장된 장소 목록을 유지하고 시간 계산 중 상태는 상단에 표시한다. revision이 바뀌면 하루 계산과 전체 동선 캐시를 무효화한다. 늦은 문서·하루 계산·전체 경로 응답이 최신 편집을 덮거나 새로운 조회의 로딩 상태를 끄지 않게 한다.
- **오류 회복:** 지금 화면에서 조회 실패와 완료/건너뛰기/제안 반영 실패를 분리한다. 다시 저장은 최신 상태와 revision을 확인한 뒤 해당 작업을 재시도한다. 반영 여부가 불확실한 요청을 무조건 반복하지 않는다. 후보 저장의 중복 요청 키와 부분 성공 안내도 연결했다.
- **초안/되돌리기:** 새 여행의 처음부터/가진 일정으로 전환은 각 입력 상태를 보존한다. 장소·예약·비용 항목·여행/하루 설정 편집기는 저장 실패 시 초안을 유지하고 변경을 버리는 취소를 확인하며, 수정 중인 시트를 내려 닫지 못하게 한다. 일정의 마지막 변경을 현재 revision에서 되돌리며 충돌을 강제 덮어쓰지 않는다.
- **인증:** 일시적인 세션 확인 통신 오류, 서버 오류, 429·잘못된 응답과 명시적인 만료를 구분하도록 수정했다. 통신 실패만으로 Keychain 세션을 지우지 않으며 `401`/정상적인 세션 없음은 계속 만료로 처리한다. 기존 쿠키 격리 수정은 보존한다. 이 재현 가능한 코드 경로를 최근 사용자 로그인 실패의 확정 원인이라고 주장하지 않는다.
- **지금/여행 중:** 앱 복귀 시 내용을 유지하며 필요한 상태를 갱신한다. 출발 전 길찾기, 방문 중 완료, 다음 장소 건너뛰기를 연결했다. 여행 시작·종료와 오늘의 흐름을 화면에 표시하고 사용자가 시작을 선택한 뒤 기존 위치/알림 안내로 이어진다. 권한 안내에는 나중에 진행하는 선택지가 있다.
- **예약 현장 확인:** 예약 목록에서 먼저 상세를 읽는다. 예약번호·관련 시각·예약 페이지·명시적인 번호 복사와 별도 편집 진입을 제공한다. 가격 추적·호텔/렌터카·취소 상세는 필요할 때 펼친다.
- **권한/접근성:** 보기 권한에는 쓰기 행동을 제한하고 서버에서도 권한을 검사한다. 읽기 전용 `SpotInformationView`에서 장소 이름·주소·계획 도착/예약 시각·체류시간·예약 요건과 상태·공식 https 링크·인원·메모·원래 통화의 비용을 확인한다. 이 화면에는 저장·입력 행동이 없다. 지도와 목록을 대체 조작 경로로 제공하며 핵심 버튼에 접근성 이름과 터치 영역을 넣었다. 날짜 스와이프는 일정 목록에 두고 지도 드래그와 분리했다. 동작 줄이기에서는 화면 전환을 완화한다.

남은 UX 범위:

- 새 여행의 입력 보존은 두 작성 방식 사이의 전환에 적용된다. 새 여행 시트 전체를 닫았다 다시 열 때까지 초안을 보관하는 기능은 아니다.
- 작은 화면·큰 글자·VoiceOver·동작 줄이기·다크 모드·지도/스크롤 제스처 전 조합을 통과했다고 주장하지 않는다. 특히 실제 VoiceOver 순서와 권한 거절 후 설정 앱 복귀는 기기 검증에 남긴다.

선행 #224가 미병합이다. #226에는 API와 Swift 계약·클라이언트가 함께 들어가고, 현재 브랜치가 그 계약을 사용하는 새 UI를 연결한다. 각 중간 브랜치의 GitHub 검사와 main으로 변경할 때의 필수 체크를 다시 확인한 뒤 순서대로 반영해야 한다.

**이번 변경의 최종 머지·NAS 배포·TestFlight 업로드는 현재 승인 범위에 포함되지 않는다.** 구현·검증·검토 가능한 PR 준비를 먼저 완료한다. 이전 릴리스의 배포 이력을 이번 새 변경의 배포 완료나 승인으로 취급하지 않는다.

새 iOS는 NAS의 새 검색/후보/미리보기 경로와 nullable 후보 식별자·요청 키 마이그레이션을 필요로 한다. API·DB 호환 확인을 앱보다 먼저 진행해야 하며 Vercel 정적 웹 배포만으로 NAS API가 바뀌지 않는다. [지도 탐색 API의 배포·롤백 설명](ios-map-planning-api.md)과 [NAS 릴리스 절차](nas-release.md)에 따라 migrate·api·realtime을 같은 대상 커밋으로 준비하고 backup을 포함한 전체 구성을 확인한다.

되돌릴 때 새 DB 필드와 저장 데이터를 삭제하지 않는다. 새 앱이 이미 설치된 상황에서는 구형 API로 단순 회귀하지 않고 설치된 앱의 요청 및 외화 소수 보존을 지원하는 호환 경로를 유지해야 한다. 최종 PR에는 실제 배포 대상·순서·되돌리기 조건을 구체적으로 적는다.
