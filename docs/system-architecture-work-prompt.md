# With J 시스템 구성 개선 작업 프롬프트

아래 내용을 새 작업의 프롬프트로 사용한다.

---

Trip Canvas 저장소의 실제 코드를 기준으로 With J의 시스템 구성을 정리하고, 배포·복구 안정성을 개선해줘. 공통 여행 엔진과 단일 API 구조를 유지하면서 이관 중인 구현과 운영 경로의 복잡도를 줄이는 것이 목표다.

## 작업 원칙

- 저장소의 최신 `AGENTS.md`와 하위 작업 지침을 먼저 읽고 따른다. 시작과 커밋 전에 원격 변경을 확인한다.
- 현재 작업 브랜치의 다른 변경을 섞지 않는다. 필요하면 최신 `origin/main` 기준의 별도 작업 공간과 허용된 이름의 브랜치를 사용한다. `main`에 직접 커밋·푸시하지 않는다.
- 먼저 실제 구현과 설정을 확인한다. 문서의 과거 설명을 현재 동작으로 단정하지 않는다.
- 계획만 제시하고 끝내지 말고, 확인 가능한 범위의 문서·코드·검증 도구를 단계별로 완성한다. 각 단계에서 발견한 사실에 따라 다음 변경 범위를 조정한다.
- 변경은 작고 검토 가능한 단위로 나누고, 관계없는 리팩터링이나 기능 추가를 하지 않는다.
- 운영 서비스 이전, 유료 자원 생성, 운영 데이터 변경, 실제 배포, PR 머지는 이 프롬프트만으로 실행하지 않는다. 필요한 준비와 검증을 끝내고 구체적인 변경·영향·복구 절차를 제시한 뒤 승인을 받는다.
- 비밀값을 출력하거나 문서에 기록하지 않는다. 운영 접근 권한이 없으면 코드로 확인한 사실과 운영에서 확인해야 할 항목을 구분한다.

## 1. 현재 시스템의 기준선 확립

웹 PWA, Next 웹, iOS, API, 인증, PostgreSQL, 실시간 중계, 외부 지도·경로 API, 백업, 배포 경로를 코드에서 추적해줘.

우선 확인할 파일과 영역:

- `api.js`, `auth.js`, `app.js`, `sync.js`, `routing.js`, `sw.js`
- `adaptive.js`, `lib.js`, `collab.js`, `price.js`, `intake.js`
- `next/src/app/api/v1/route-deps.ts`
- `next/src/server/application/`, `next/src/server/infrastructure/`, `next/src/server/config/`, `next/src/server/auth/`, `next/src/server/realtime/`, `next/src/server/routing/`
- `next/src/features/trip-state/`와 `next/src/app/`의 웹 화면
- iOS의 API 클라이언트, 인증, 문서 저장, 캐시, 실시간 연결
- `deploy/`, `next/Dockerfile`, `vercel.json`, `.github/workflows/`, `scripts/verify-all.sh`
- `docs/architecture.md`, `docs/backend-architecture.md`, `docs/nas-deployment.md`, `docs/backup-restore.md`, `docs/supabase-migration.md`

다음 산출물을 기존 문서 구조에 맞춰 작성하거나 갱신해줘:

1. 실제 실행 구성도와 요청·저장·실시간 갱신 흐름.
2. 구성요소별 책임, 배포 위치, 상태 보유 위치, 장애 시 사용자 영향 표.
3. 코드로 확인한 사실, 문서에만 있는 설명, 운영 확인이 필요한 항목의 구분.
4. 문서와 코드의 불일치 수정. 과거 구조는 이력으로 명확히 표시.

특히 서버 경로 캐시, 실시간 중계, NAS 인가 계층을 확인해줘. 과거의 “서버는 직선 추정만 사용”, “실시간 없음”, “모든 권한은 Supabase RLS가 결정” 설명을 그대로 재사용하지 않는다. 코드 존재만으로 운영 활성화를 단정하지 않는다.

완료 기준: 주요 읽기·쓰기 경로와 배포 대상이 소스 근거로 연결되고, 현재 구조와 이관 이력이 혼동되지 않는다.

## 2. 배포와 복구 안정화

기존 도구를 먼저 확인하고 부족한 부분만 보완해줘.

- 웹과 NAS API가 서로 다른 버전일 때의 호환성 문제를 조사한다. API 선배포와 구버전 클라이언트 호환을 기본으로, 필요한 경우 기능 지원 여부 확인 방식을 제안·구현한다. 단순한 기존 방식으로 해결되면 새로운 체계를 만들지 않는다.
- API·실시간 중계·DB 마이그레이션이 변경될 때 각각 무엇을 빌드하고 배포해야 하는지 확인한다. API만 재배포해서 다른 구성요소가 옛 버전으로 남는 일을 막는다.
- 코드 버전, 스키마 적용 상태, 외부 경로 상태를 확인할 기존 방법을 연결하고, 부족하면 최소한의 점검 도구를 추가한다. 단순한 401 응답 확인과 실제 로그인·여행 읽기·저장 검증을 구분한다.
- 기존 백업의 성공·실패 감지, 보관 정책, 오프사이트 복제 여부를 조사한다. 덤프 파일 존재와 복구 성공을 구분한다.
- 운영 DB와 분리된 임시 환경에서 복구 리허설을 수행할 재현 가능한 절차를 마련한다. 민감한 운영 덤프를 임의로 내려받지 않는다. 실행한 데이터와 범위를 보고한다.
- 복구 목표 시간과 허용 가능한 데이터 손실 범위는 현재 절차로 가능한 수준을 먼저 산정하고, 사용자 결정이 필요한 목표값을 별도로 제시한다.
- 코드 롤백, 스키마 호환, 데이터 복구를 별도로 문서화한다. 새 PostgreSQL의 변경이 예전 Supabase에 자동 반영되지 않으므로 주소나 플래그 변경만으로 안전하게 롤백된다고 쓰지 않는다.

완료 기준: 배포 대상 누락을 확인할 수 있고, 독립된 환경에서 검증 가능한 복구 절차와 결과가 남는다. 운영에서 미확인된 사항은 명시한다.

## 3. 이관 분기의 종료 조건 정리

`LEGACY / DUAL_READ / NEW_BACKEND`, Supabase 토큰과 자체 인증, 레거시 Gateway·Repository의 실제 참조를 조사해줘.

- 도메인마다 읽는 저장소, 쓰는 저장소, 인증·인가 주체, 폴백 조건을 표로 정리한다. DUAL_READ의 동작이 도메인마다 같은지 확인한다.
- 코드 기본값과 운영 설정을 구분한다. 설정 누락이나 잘못된 값이 의도하지 않은 레거시 접근으로 이어지는지 검토한다.
- 각 분기에 데이터 이관 검증, 활성 클라이언트 호환, 관찰 기간, 복구 준비 등 구체적인 제거 조건을 붙인다.
- 제거 조건을 충족했다는 근거가 있는 코드만 정리한다. 근거가 없는 레거시 경로를 사용하지 않을 것이라고 추정해 삭제하지 않는다.
- 새 API의 권한 검사와 revision 충돌 처리가 모든 관련 진입점에서 유지되는지 확인한다.

완료 기준: 남겨야 하는 분기에는 이유와 종료 조건이 있고, 제거한 분기는 계약·권한·동기화 회귀 검증을 통과한다.

## 4. 웹 구현의 장기 병행 축소

정적 웹과 Next 웹의 실제 기능을 비교하고, 최종 웹 구현을 결정할 자료를 만들어줘. Next 전환을 이미 확정된 결정으로 취급하지 않는다.

- 지도·검색·경로, 일정 편집, 예약, 로그인, 동기화·충돌, 협업, 가져오기·공유, 실행 취소, PWA·오프라인 동작을 비교한다.
- 화면이나 파일이 있다는 사실과 실제 기능 검증 완료를 구분한다.
- 현재 PWA 유지와 Next 전환을 유지보수 부담, 기능 차이, 캐시·오프라인 요구, 배포 위험으로 비교하고 추천안을 낸다.
- 추천안에 기능별 전환 순서, 회귀 검증, 복귀 방법, 구 구현 제거 조건을 포함한다.
- 결정에 의존하지 않는 문서·검증 보완은 진행한다. 최종 웹 선택에 대한 사용자 결정을 받은 뒤 그 방향의 구현을 진행한다.

완료 기준: 장기적으로 유지할 웹 구현의 선택 근거와 기능별 전환 기준이 명확하며, 두 웹에 같은 기능을 계속 중복 구현하는 범위가 줄어든다.

## 5. 공통 엔진과 데이터 모델 검증

- 여행 판단은 기존 순수 JS 엔진에 유지하고 Swift나 화면 코드에 복제하지 않는다.
- 같은 엔진이라도 입력 시각·시간대·경로 캐시·거절 이력이 다르면 결과가 달라질 수 있다. 웹과 API의 입력 구성과 응답 계약을 비교한다.
- 기존 Swift 계약 검증과 엔진 테스트를 활용하고, 발견한 불일치에 필요한 테스트만 추가한다.
- JSON 문서의 알 수 없는 필드 보존, revision 충돌, 삭제 동기화, 멤버 권한을 확인한다.
- 여행 전체 저장의 충돌 문제가 실제로 확인되지 않으면 장소 단위 API, CRDT, 이벤트 소싱 등을 선제적으로 도입하지 않는다. 추가 분리가 필요하다면 관측 근거와 최소 변경안을 제시한다.

완료 기준: 플랫폼 간 결과 차이의 원인이 입력 차이인지 구현 오류인지 설명되고, 수정한 오류에는 의미 있는 회귀 검증이 있다.

## 검증과 최종 보고

- 단계별로 변경에 맞는 검증을 실행한다. 단순 문서 수정에 구현을 따라 쓰는 테스트를 추가하지 않는다.
- 릴리스 단계에서는 저장소 지침에 따라 `npm run verify:all`을 실행하고, 웹 자산 변경 시 버전을 갱신한다. SKIP은 PASS로 보고하지 않는다.
- 외부 키·실기기·운영 접근이 필요한 검증은 실제 수행 여부와 제한을 명확히 남긴다.
- 최종 보고에는 완료한 변경, 소스 근거, 실행한 검증과 결과, 남은 위험, 사용자 결정이 필요한 사항, 다음 실행 순서를 포함한다.
- 테스트 작성과 통과, 도구 준비와 복구 성공, 코드 변경과 운영 배포를 각각 구분한다.

우선 1단계로 사실관계를 확정하고, 그 결과를 바탕으로 2단계부터 작은 변경 단위로 진행해줘. 기본 방향은 공통 엔진과 단일 API 유지다. 호스팅 이전이나 서비스 분리는 가용성 요구와 측정 결과를 근거로 별도 제안해줘.
