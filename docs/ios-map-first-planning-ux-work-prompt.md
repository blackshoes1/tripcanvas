# With J iOS — 지도에서 시작하는 여행 일정 UX 개발 프롬프트

작성일: 2026-09-16

아래 내용을 개발 작업의 실행 프롬프트로 사용한다. 이 문서 작성 자체는 앱 구현·머지·배포를 실행하라는 요청이 아니다.

## 1. 목표와 사용자가 정한 방향

With J iOS를 **지도를 보며 갈 곳을 발견하고, 장소를 모아 여러 날의 현실적인 여행 일정으로 완성하는 앱**으로 개선해줘.

사용자는 장소의 방문 순서를 정하기 전에 어디에 갈지부터 찾는다. 이때 **지도를 보며 장소를 발견하고 서로의 위치와 동선을 파악하는 방식**을 선호한다고 명확히 말했다. 이 선호를 기본 작성 경험의 기준으로 삼아줘.

핵심 흐름은 다음과 같다.

> 여행 지역 지도 열기 → 주변 장소 탐색 → 날짜 미정으로 ‘가고 싶은 곳’에 담기 → 날짜에 배치 → 순서·시간 조정 → 하루 예산과 예약 준비 확인

- 기존 카카오·Google 지도를 기반으로 확장한다. 검색은 지도 안에서 탐색을 돕는다.
- 갈 곳을 모으는 동안 방문일·순서·체류시간·비용을 모두 정하도록 요구하지 않는다. 날짜가 이미 정해진 장소는 바로 해당 날에 넣을 수 있게 한다.
- 장소를 담아도 지도와 탐색 맥락을 유지하고 다음 장소를 계속 찾을 수 있게 한다.
- 지도 아래 접었다 펼치는 목록으로 후보 확인과 일정 편집을 연결한다. 목록을 크게 펼쳐 집중해서 편집할 수도 있어야 한다.
- 추천에는 이유·미리보기·선택권을 제공한다. 사용자 확인 없이 일정 재배치, 비용 확정, 예약 완료 처리를 하지 않는다.
- 제품명은 With J, 제안의 서명은 From J를 사용한다. 기존 브랜드와 종이빛 팔레트를 유지하면서 정보 구조와 조작을 개선한다.

## 2. 시작 전에 확인할 코드와 기준

최신 `AGENTS.md`와 수정 영역의 하위 지침을 읽고 원격을 fetch한다. 로컬 작업과 다른 작업 공간을 확인해 기존 변경을 섞거나 덮어쓰지 않는다. 프로젝트 지침에 맞는 별도 브랜치/작업 공간에서 진행하고 main에는 직접 커밋·푸시하지 않는다.

이번 UX 검토는 TestFlight 0.1.0 (34)의 `df11e2f3a3f78a06a65dff96d0db884c8b7bac12`를 기준으로 했다. 확인 당시 `origin/main`은 `ebbf45b`였고 관련 iOS 수정은 `fix/ios-plan-refresh` / PR #224에 묶여 있었다. **실행 시 최신 main·PR·배포 빌드 상태를 다시 확인**하고, 이미 병합된 변경을 재적용하지 않는다. 미병합 수정이 필요하면 그 변경을 보존하는 작업 기준을 정한다.

이미 수정된 일정 스와이프/행 탭 충돌, 저장 후 재계산 요청 누락, 카카오 지도 표시, 인증 쿠키 처리는 보존한다. 과거 사용자 증상을 현재 미수정 버그로 단정하지 않는다. 최근 일시적 로그인 실패의 원인은 확정되지 않았으므로 그 원인을 이 UX 작업에서 추측해 고치지 않는다.

우선 읽을 파일·영역:

- `ios/TripCanvas/Features/Trips/`: 여행 목록·생성·붙여넣기·지금/일정 진입.
- `ios/TripCanvas/Features/Plan/`: 일정 화면·편집기·하루 계산과 저장 상태.
- `ios/TripCanvas/Features/Map/`: 지도 엔진·네이티브 지도 컨테이너·검색 모델과 서비스.
- `ios/TripCanvas/Features/Collab/`: 가고 싶은 곳·날짜 배치·그룹 제안.
- `ios/TripCanvas/Features/Booking/`, `Today/`, `TravelMode/`, `Core/Auth/`, `DesignSystem/`.
- `ios/TripCanvas/Core/Models/TripDocument.swift`, `TripBooking.swift`, `Contract.swift`, `Services/`.

## 3. 진행 방법과 우선순위

아래 A부터 F까지 단계별로 구현·검증한다. 한 번에 거대한 PR을 만들지 말고 독립적으로 검토 가능한 단위로 나눈다. 각 단계가 끝나면 구현·테스트 결과·미검증 항목을 기록하고 다음 단계로 이어간다. 와이어프레임이나 목업만 만들고 기능이 완성됐다고 보고하지 않는다.

첫 구현 단위는 **A: 빈 여행의 지도 탐색과 연속 담기**다. 이후 B, C, D, E 순서로 연결한다. F의 상태·권한·접근성 기준은 각 단계에 적용하고, 관련 후속 화면 개선은 별도 단위로 마무리한다.

### A. 지도에서 장소 찾고 연속으로 담기

1. 일정이 비어 있어도 여행 지역 지도를 보여준다. 시작 지역이 불명확하면 도시/지역 선택을 제공한다. 한국어 검색어만으로 해외 여행을 국내로 오인하지 않도록 명시적으로 선택한 지역과 지도 중심을 활용한다.
2. 지도 위에 검색창과 음식점·카페·관광·숙소 등 간결한 업종 필터를 제공한다. 지도를 옮기면 ‘이 지역에서 찾기’를 표시한다. 현재 화면의 범위와 검색 결과 범위를 일치시키거나 제한을 명확히 설명한다.
3. 검색 결과 핀을 누르면 지도 아래 작은 장소 카드에 이름·지역/주소·분류와 ‘가고 싶은 곳에 담기’를 보여준다. 상세 편집 화면을 자동으로 열지 않는다. 좌표만 선택한 경우 실제 상호로 오인하지 않게 하고 장소 검색/이름 입력으로 이어준다.
4. 명시적으로 담기를 누르면 기존 후보 저장 경로에 저장한다. 성공한 장소는 ‘담았어요’로 바꾸고 지도·검색어·확대 수준을 유지한다. 반복 탭과 동일 장소 중복을 처리하되, 이름만 같다고 다른 지점을 합치지 않는다.
5. 탐색 결과·날짜 미정 후보·날짜 배정 장소의 핀을 색뿐 아니라 모양/라벨로 구분한다. 날짜 미정 후보에는 방문 순서 번호나 경로 연결선을 붙이지 않는다.
6. 하단의 ‘담은 장소 N곳’ 목록을 펼치면 후보를 확인하고 날짜 배치로 이어갈 수 있게 한다. 사진·평점 등 부가 정보는 실제 데이터가 있을 때만 표시하고 출처 표시 규칙을 따른다.
7. 검색 실패·무결과 화면에 다시 검색과 ‘검색어로 직접 담기’를 제공한다. 이름만 저장한 장소는 위치 미정으로 남기고 동선에 포함된 것처럼 표시하지 않는다.

구현 시 주의:

- 현재 Google 지도에는 장소 탭 시 이름·좌표·Place ID를 받는 연결이 있다. 카카오 컨테이너의 현재 일반 탭은 좌표만 전달한다. 사용 중인 iOS SDK의 이벤트와 장소 ID 의미를 공식 문서로 확인하고, 웹 SDK 제약을 네이티브에도 그대로 단정하지 않는다.
- 카카오는 필요하면 서버의 장소 검색 결과를 선택 가능한 핀으로 올린다. 주변 검색으로 가장 가까운 상호를 추측해 사용자가 누른 장소라고 확정하지 않는다.
- 기존 검색은 검색어+근처 좌표 중심이다. 업종·화면 범위 검색이 이미 되는 것으로 가정하지 말고 필요한 API와 정규화 계약을 추가한다. REST 비밀 키는 서버에 둔다.
- 검색 결과나 후보 핀이 추가될 때 기존 지도 fit 로직이 사용자의 시점을 되돌리지 않게 한다. 오래된 검색 응답이 최신 지도/지역의 결과를 덮어쓰지 않게 한다.
- 지도 위의 가로·세로 드래그는 지도 이동으로 처리한다. 날짜 변경은 날짜 선택기나 일정 목록의 지정 영역에서만 처리하고, 하단 목록 스크롤·시트 높이 조절·지도 이동의 제스처 영역을 구분한다.
- 사용자의 탐색 의도에 맞춰 조회하고, 지도 이동 중 연속 호출이나 모든 핀의 상세 동시 조회를 피한다. 지도 데이터 캐시·표시·출처는 각 제공자 조건에 맞춘다.

완료 기준: 국내·해외의 빈 여행에서 장소를 찾고 5곳 이상 연속으로 담은 뒤, 화면을 다시 열어 후보가 보존됨을 확인한다. 담기 중 지도 시점이 튀지 않고 이름·주소·좌표가 정확히 연결되며 중복 탭으로 후보가 늘지 않는다.

### B. 모은 장소를 날짜에 배치하고 동선 조정하기

1. 여행 전체 개요에 날짜/요일·지역/제목·주요 장소·이동시간·예상 종료·시간 미정 항목을 보여준다. 하루씩 오가지 않아도 빈 날과 일정이 많은 날을 비교할 수 있게 한다. 장소 수만으로 과밀을 판단하지 않는다.
2. 지도와 하단 일정 목록의 선택 상태를 연결한다. 목록에서 장소를 고르면 핀/해당 구간을 강조하고, 핀 선택은 목록의 해당 장소로 연결한다. 목록을 펼친 상태와 선택 날짜를 불필요하게 초기화하지 않는다.
3. 후보를 넣을 때 방문 날짜뿐 아니라 ‘점심 뒤에 넣기’ 같은 삽입 위치를 선택하게 한다. 기존 일정 사이에도 ‘여기에 추가’를 제공한다. 모든 장소를 맨 뒤에 넣고 다시 끌도록 요구하지 않는다.
4. 장소를 다른 날로 이동할 때 목적 날짜·요일·지역과 들어갈 위치를 보여준다. 선택한 여러 장소를 함께 옮기는 동작은 순서와 예약 제약을 유지하고, 직접적인 버튼/메뉴 경로도 제공한다.
5. 순서나 날짜를 바꾸기 전후의 이동시간·종료시각·예약까지 여유 변화를 비교할 수 있게 한다. 아직 경로/체류시간이 없는 경우 변화값을 정확한 계산처럼 말하지 않는다.
6. 기존 후보 날짜 추천·그룹 제안을 일정 작성 흐름에 연결한다. 새 최적화 엔진을 만들지 말고 공통 엔진을 확장한다. 고정 예약·완료 항목·꼭 가고 싶은 곳을 보호하고 변경은 확인 후 반영한다.

완료 기준: 후보를 원하는 일정 사이에 넣고, 다른 날의 특정 위치로 이동하고, 지도와 목록에서 같은 결과를 확인할 수 있다. 전체 개요·후보 상태·시간·비용이 함께 갱신되고 CAS 충돌 시 저장 여부가 명확하다.

### C. 하루의 기본 틀과 현실적인 시간 계획

1. 생성 후에도 여행 시작일·기간/일자 추가, 하루 제목·출발 시각·출발 장소/이월 여부·기본 이동수단을 앱에서 조정할 수 있게 한다. 기존 문서 필드와 공통 앵커 규칙을 재사용한다.
2. 날짜 축소/삭제나 시작일 변경 시 영향을 받는 일정·후보·예약을 미리 보여준다. 명소를 조용히 버리거나 외부에서 확정한 예약 날짜를 함께 자동 이동하지 않는다. 보존·이동·삭제 의도를 확인해 처리한다.
3. 하루 시작·이동·체류·예약 대기·식사/휴식·종료를 이해하기 쉬운 시간 흐름으로 보여준다. 종료시각을 자정을 넘었을 때만 표시하지 않는다. 식사/휴식은 사용자가 배치하거나 확인한 제안으로만 일정에 넣는다.
4. 체류시간 미정은 현재 계산 규칙인 0분을 유지하되 ‘머무는 시간 미정 N곳’을 표시한다. ‘미정’과 ‘0분, 바로 이동’을 구분한다. 제안 체류시간을 사용자의 계획값에 몰래 채우지 않는다.
5. 예약·입장 시각은 1분 단위로 입력할 수 있게 한다. 자동 도착 예상, 내가 정한 도착 시각, 외부 예약 시각을 구분한다. 모든 장소에 고정 시각을 입력하도록 강요하지 않는다.
6. 장소 편집은 자주 쓰는 정보부터 보여주고 비용·숙소 등 추가 설정은 필요할 때 펼친다. 어떤 여행/날짜의 장소를 편집하는지 알 수 있게 한다.

완료 기준: 11시 출발인 하루, 12:07 예약, 체류시간 미정 장소, 자정 이후 종료, 전날 숙소/공항 출발이 각각 정확히 표시된다. 날짜 조정 후 고정 예약과 숨은 문서 필드가 손실되지 않는다.

### D. 하루 예산 설정과 비용 표시

1. **하루 예산은 사용자가 정하는 값**, **예상 비용은 입력/확인된 항목의 합계**로 분리한다. 예산 미설정과 예산 0을 구분한다. 일정 상단의 비용 영역에서 예산을 설정·수정할 수 있게 한다.
2. 일정 상단에 예산·현재 예상 비용·예산 대비 차이·비용 미정 항목 수를 표시한다. 미정 금액이 있을 때 차이를 확정적인 잔여 예산으로 보이지 않게 한다. 예산 초과는 설명하되 사용자의 장소 추가를 막지 않는다.
3. 비용 영역을 누르면 장소/항목별 내역을 펼치고 식사·입장료·교통·숙박 등의 비용을 입력·수정할 수 있게 한다. 장소 수집 시 비용 입력은 선택 사항으로 둔다.
4. 무료(확인한 0원), 비용 미정, 일부 금액만 확인한 경우를 구분한다. 현재 입력 처리에서 0이 nil로 바뀌는 부분까지 확인한다. 정보 없음이나 조회 실패를 무료로 처리하지 않는다.
5. 1인 기준/일행 전체 기준과 적용 인원수를 명시한다. 개인 항목·공유 항목을 합칠 때 의미를 확인하고, 화면 라벨만 바꿔 금액을 임의 곱셈하지 않는다.
6. 외화는 원래 통화와 금액을 보존하고 원화 환산은 ‘약’과 환산 기준/시점을 표시한다. 현재 서버의 폴백 환율을 실시간 환율처럼 설명하지 않는다. 소수 통화의 입력·저장·반올림을 검증한다.
7. 기존 하루 비용 계산의 포함 범위와 누락을 확인한다. 장소 금액·일부 교통비·예약의 날짜별 배분이 이미 있으므로 숙박/입장권/장소 비용을 중복 합산하지 않는다. 자동 계산되지 않은 교통비는 포함된 것처럼 표시하지 않는다.
8. 장소의 날짜 이동·삭제·인원/통화 변경 시 관련 날짜와 여행 합계를 갱신한다. 예산/새 비용 필드는 웹·iOS 왕복 저장에서 보존되고 동일한 공통 계산 결과를 사용해야 한다.

완료 기준: 예산 미설정·0원·미입력, 예산 초과, 외화/소수 금액, 1인/전체, 숙박 연결 중복, 날짜 이동 전후 합계를 합성 데이터로 검증한다. 사용자는 하루 합계에 무엇이 포함됐는지 알 수 있다.

### E. 명소의 예약 요건과 참고 가격

1. 지도 장소 카드와 일정 항목에 예약 요건을 표시한다: **예약 필수 / 예약 권장 / 예약 없이 입장 가능 / 확인 필요**. 근거가 없는 상태는 확인 필요로 둔다.
2. 명소의 요건과 **사용자의 예약 전/완료 상태**를 분리한다. 기존 `bookAt`은 예약·입장 시각이며 예약 완료 증거가 아니다. `bookingId`는 현재 숙박 연결 용도이므로 명소 티켓 상태를 억지로 재사용하지 않는다.
3. 공식 명소/입장권 제공처의 허용된 데이터에서 참고 가격을 가져온다. 장소 식별, 데이터 이용 조건, 현재 연동 가능 여부를 확인하고 가장 작은 실제 연동부터 구현한다. 기존 호텔·렌터카 시세 기능이 명소 입장권 조회를 제공한다고 가정하지 않는다.
4. 참고 가격은 금액/범위·현지 통화·성인/어린이·1인/총액·권종·적용 날짜/시즌·포함 조건·출처 링크·확인 시점을 함께 가진다. 확보하지 못한 조건은 모름으로 표시한다. 최저가·일반 가격대·선택 날짜의 실제 결제 가격을 구분한다.
5. Google `reservable`은 예약 지원 여부이지 필수 여부가 아니다. `priceLevel`/`priceRange`는 해당 날짜의 입장권 가격을 보장하지 않는다. 카카오 기본 장소 검색만으로 입장료와 예약 필수 여부를 채울 수 있다고 가정하지 않는다.
6. 조회 결과와 사용자가 확인한 계획 비용을 분리한다. ‘예상 비용에 반영’에서 금액/범위·인원을 확인한 뒤 반영하고, 갱신된 참고 가격으로 사용자의 확정 금액을 덮어쓰지 않는다. 범위만 있을 때 임의 중간값을 확정하지 않는다.
7. 공식 예약 페이지와 ‘예약 완료 표시’를 제공한다. 링크를 열었다고 완료 처리하지 않는다. 확인된 예약 시각·인원·가격을 일정/비용과 연결하고, 예약 시각은 동선 조정 시 보호한다.
   이 단계의 범위는 공식 페이지 안내와 사용자가 확인한 예약 상태 기록까지다. 실제 예약 신청·티켓 구매·결제 자동화는 포함하지 않는다.
8. 하루 일정 상단에 ‘예약할 곳 N곳’을 제공하고 해당 항목으로 이동한다. 확인 필요 항목을 예약 필수 건수에 섞지 않는다. 참고 가격이 있다고 예약 가능 좌석/시간이 남았다고 표시하지 않는다.
9. 데이터 없음·오래된 정보·연결 실패에서는 출처/공식 페이지 확인과 직접 입력을 제공한다. 사용자가 입력한 정보와 외부 조회 정보를 구분한다. AI가 기억으로 가격이나 예약 규정을 만들어 넣지 않는다.

외부 데이터 연결이 막힌 경우에는 확보 가능한 실제 조회, 상태 모델·화면, 직접 입력·공식 링크 경로를 구현하고 **자동 조회가 안 되는 범위와 필요한 연결을 명시**한다. 가짜 응답을 운영 기능에 넣거나 목업 테스트 통과를 실제 연동 완료로 보고하지 않는다. 새 유료 계약/별도 계정이 필요한 경우 구체적인 선택지·비용·지원 범위를 확인해 결정받고, 영향 없는 개발은 계속한다.

완료 기준: 예약 필수/권장/불명, 예약 전/완료, 무료/가격 없음, 성인·어린이/권종 차이, 날짜별 가격, 조회 실패/오래된 정보, 비용 반영 확인을 검증한다. 실제 제공처 연동 테스트와 대역 테스트 결과를 구분한다.

### F. 공통 신뢰·편집·접근성과 후속 화면

- **저장과 계산:** 저장 후 변경한 일정과 스크롤을 유지하고 시간/구간만 계산 중으로 표시한다. 이전 값을 최신 값처럼 보이지 않게 한다. 계산 실패가 저장 실패로 보이거나 과거 응답이 새 순서를 덮어쓰지 않게 한다.
- **작업별 오류 회복:** 읽기 실패·장소 저장 실패·완료 표시 실패를 각각 설명한다. ‘다시 저장’은 해당 변경을 재시도해야 하며 단순 조회로 대체하지 않는다. 이미 적용된 요청인지 불확실하면 서버 상태와 revision을 확인해 중복 쓰기를 피한다.
- **초안과 되돌리기:** 새 여행의 ‘처음부터/가진 일정으로’ 전환, 검색/지도 이동, 편집기 닫기에서 입력을 보존한다. 삭제·재정렬·날짜 이동은 마지막 변경을 되돌릴 수 있게 하고, 협업 충돌이 있으면 다른 사람의 변경을 전체 스냅샷으로 덮어쓰지 않는다.
- **로그인:** 잘못된 자격 증명·통신 장애·서버 오류·만료를 구분한다. 이메일 앞뒤 공백만 정리하고 비밀번호는 변경하지 않는다. 일시적인 세션 확인 실패를 곧바로 만료로 간주하는 경로를 재현 테스트 후 수정한다. 최근 사용자 로그인 실패의 원인을 이 코드 경로로 확정했다고 설명하지 않는다.
- **지금 화면:** 여행 전 ‘일정’, 여행 중 ‘지금’의 기존 진입 규칙을 존중한다. 출발 전에는 길찾기, 방문 중에는 완료 행동을 강조하고 다음 장소에도 건너뛰기를 제공한다. 앱 복귀 시 필요한 최신 상태를 가져오되 계속 조회하지 않는다.
- **여행 중 진입:** 기존 여행 시작·종료·위치/알림 안내와 오늘의 흐름 구성 요소가 실제 화면에 연결되는지 확인한다. 여행 당일 사용자가 시작을 선택한 뒤 관련 권한 안내를 연결한다.
- **예약 현장 확인:** 예약번호 입력·명시적인 복사·예약 페이지·관련 시각을 먼저 확인할 수 있게 한다. 가격 추적의 상세 조건은 필요할 때 펼친다.
- **권한:** 기존 OWNER/EDITOR/VIEWER 규칙을 UI와 서버 양쪽에서 지킨다. 보기 권한에는 길찾기·일정/예약 확인을 제공하고 저장·후보 추가·완료 등 허용되지 않는 변경 행동을 노출하지 않는다.
- **접근성:** 작은 iPhone, 큰 글자, VoiceOver, 동작 줄이기, 라이트/다크 모드에서 확인한다. 핵심 버튼의 터치 영역을 확보하고 색만으로 상태를 구분하지 않는다. 지도 핀에 해당하는 목록과 드래그를 대신하는 이동 메뉴를 제공한다. 큰 글자에서 목록 전체 높이를 고정해 내용을 자르지 않는다.

## 4. 구현 원칙과 데이터 무결성

- UX의 주 대상은 iOS다. API·공통 엔진·정규화·웹 호환 수정은 필요한 범위에 한정하고 Next 웹 전체 개편으로 확장하지 않는다.
- 판단과 도메인 계산은 공통 엔진 및 기존 API 계층에서 수행한다. iOS에 별도의 경로 최적화·비용 합산·예약 충돌 판단 엔진을 복제하지 않는다. iOS는 입력, 화면 상태, 표현을 담당한다.
- `dayAnchor`/`dayStartAnchor`, 예약 시각/도착 계획/자동 예상, 계획 체류/추천 체류를 구분한다. 국내·해외 이동시간의 실제 경로와 추정을 표시한다.
- 새 필드는 계약·정규화·서버 검증·저장·읽기·필요한 마이그레이션·구버전 호환까지 연결한다. 하드코딩된 완성 문장 대신 값과 의미를 전달한다. Swift의 정수 디코딩 경계를 검증한다.
- 여행 문서는 기존 `JSONValue` 원문 보존 방식을 유지한다. `who`, `split`, `hours` 등 모르는 필드와 외부에서 입력한 예약 정보가 저장 후 사라지면 안 된다.
- NAS API·PostgreSQL·기존 서비스/Repository·revision CAS를 사용한다. 예전 Supabase 직접 경로를 되살리거나 새 인증/충돌 엔진을 추가하지 않는다.
- 후보·장소의 제공자 식별자를 보존하고 다른 제공자의 ID를 같은 필드 의미로 섞지 않는다. 개인 여행과 공유 여행에서 접근 범위가 올바른지 확인한다.
- 장소/가격 데이터의 캐시·보존·출처·지도 표시 조건은 구현 시점의 공식 문서로 확인한다. 비밀 키·토큰·개인정보를 번들이나 로그에 노출하지 않는다. 지도 타일 오프라인 캐시를 만들지 않는다.
- 작업 중 발견한 무관한 코드 정리는 하지 않는다. 실제 기능에 필요한 최소 구조를 사용하고 미래의 모든 제공자를 위한 과도한 추상화를 만들지 않는다.

## 5. 검증 시나리오와 산출물

단계마다 실제 동작을 검증하는 테스트를 작성한다. 버그 수정은 가능한 한 수정 전 재현 실패와 수정 후 통과를 남긴다. 단순 UI 문자열/구현 구조를 복제하는 테스트로 완료를 주장하지 않는다.

다음 시나리오를 합성 여행/계정으로 확인한다.

1. 국내·해외 지역 선택 → 빈 지도 탐색 → 지역 이동 후 검색 → 핀 선택 → 후보 5곳 연속 담기 → 앱 재진입 후 보존.
2. 중복 탭·동명이점·좌표 미정·검색 무결과·통신 끊김·오래된 검색 응답·계정/여행 전환 처리.
3. 후보를 일정 중간에 넣기 → 여러 날 개요 비교 → 다른 날짜/삽입 위치로 이동 → 순서 변경 → 지도·시간·비용 갱신 → 되돌리기.
4. 지도 이동·목록 세로 스크롤·날짜 가로 스와이프·행 선택·재정렬이 충돌하지 않고 탐색 시점과 편집 초안을 보존.
5. 늦은 출발·1분 단위 예약·체류시간 미정·일자 이월·자정 초과·여행 날짜 조정의 정확한 결과와 고정 예약 보존.
6. 하루 예산/비용 미정/무료/초과, 인원 기준, 외화·소수·환산, 예약 중복 제외와 날짜 이동 후 비용 내역.
7. 명소 예약 요건·사용자 예약 상태·권종/인원/날짜별 참고 가격, 출처/확인 시점, 미연결 폴백, 비용 반영 확인.
8. 저장 성공 후 계산 실패·조회 실패·동시 편집 충돌·권한 거절·오프라인 복귀에서도 상태를 정확히 설명하고 안전하게 복구.
9. OWNER/EDITOR/VIEWER의 화면과 서버 권한, iOS 저장 후 웹 재조회/재저장에서 새 필드와 기존 필드 보존.
10. 작은 화면·큰 글자·VoiceOver·동작 줄이기·다크 모드, 실제 국내/해외 지도 선택과 길찾기 앱 복귀.

API/도메인 테스트, Swift 계약 테스트(`swiftParity` 포함), XCTest, 필요한 UI 조작 검증을 수행한다. 실제 지도/데이터 제공처를 사용한 검증과 모의 응답 검증을 구분한다. 기기에서만 검증할 수 있는 것은 미검증으로 남기고 구체적인 확인 절차를 제공한다.

릴리스 준비 시 `npm run verify:all` 전체 게이트를 실행하고 PASS/FAIL/SKIP을 정확히 기록한다. 개발 중에는 변경에 맞는 검증을 먼저 실행하고 새 변경·실패 이유 없이 같은 게이트를 반복하지 않는다. 이 프롬프트 문서만 작성하는 작업에는 앱 전체 테스트가 필요하지 않다.

산출물:

- 단계별 실제 구현과 의미 있는 회귀 테스트.
- 최신 상태 기준의 구현/미검증/외부 연결 필요 항목 목록.
- 주요 사용자 흐름을 보여주는 화면 캡처 또는 짧은 조작 기록. 테스트용 데이터임을 표시한다.
- PR에 문제와 변경 후 행동, 검증 결과, 사용자/프로덕션 영향, API·DB·앱 배포 대상, 되돌리는 방법 기록.
- 사용자가 추가 결정해야 하는 외부 제공처/데이터 조건이 있으면 구체적인 지원 범위와 함께 정리.

## 6. 머지와 배포 경계

구현·검증·검토 가능한 PR 준비까지 진행한다. 운영 머지·NAS 배포·TestFlight 업로드는 현재 대화에서 해당 릴리스에 대한 기존 승인이 있는지 확인한다. 승인이 있으면 재요청하지 않고 필수 게이트와 절차를 따른다. 승인이 없다면 변경과 검증 결과를 준비한 뒤 해당 단계의 진행 여부를 요청한다. 이 문서의 작성만으로 새 릴리스 승인이 생겼다고 해석하지 않는다.

main 머지는 웹 프로덕션 배포와 연결된다. API/DB 변경이 있으면 `deployment:plan`과 NAS 릴리스 문서에 따라 앱/서버 호환성 및 선배포 순서를 정하고, migrate·api·realtime을 같은 커밋으로 준비한다. 필수 체크가 실패한 상태를 통과로 취급하지 않는다.

완료 보고에서는 앱 구현, 자동 테스트, 실제 지도/제공처 검증, TestFlight 업로드, 실기기 확인, 프로덕션 반영을 각각 구분한다.
